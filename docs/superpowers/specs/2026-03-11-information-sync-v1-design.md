# 信息聚合同步闭环 v1 设计文档

日期：2026-03-11
状态：approved-for-planning
来源：用户直接批准的下一阶段需求，基于已完成的 stock detail v1

说明：本文档定义 stock detail v1 之后的下一阶段功能：通过详情页内手动触发，完成单股公告与新闻的同步、入库和展示刷新。实际执行仍以 `docs/02-module-registry.md`、对应模块文档和 `memory/progress.md` 为准。

## 1. 背景

当前项目已经完成：

- watchlist MVP
- backend / frontend / data-layer
- 本地一键运行
- stock detail v1

个股详情页已经具备：

- 从 watchlist 列表进入
- 详情聚合接口
- 价格上下文、公告、新闻区块结构

下一阶段目标不再是扩页面骨架，而是把详情页中的**公告 + 新闻**推进到“应用内可触发同步、可入库、可刷新展示”的闭环。

## 2. 本轮目标

本轮定义的下一阶段为：**信息聚合同步闭环 v1**。

首条用户路径为：

1. 用户从 watchlist 进入 stock detail 页面
2. 用户点击“同步公告 / 新闻”
3. 后端拉取该股票的公告与新闻
4. 后端将数据增量写入本地数据库
5. 前端重新读取详情接口并展示更新后的公告 / 新闻列表

本轮要求：

- 公告与新闻一起做
- 数据接入与存储优先
- 同步通过应用内触发完成
- 同步接口与详情读取接口分离
- 同步失败不应影响已有详情读取

## 3. 非目标

本轮明确不做：

- 批量同步整个 watchlist
- 自动定时同步
- 后台任务调度器
- 复杂新闻 / 公告标签体系
- AI 摘要与结论生成
- 复杂去重 / 相似度算法
- 多来源融合策略平台化

## 4. 推荐方案

采用 **“详情页内单股手动同步机制”** 的方案。

### 4.1 方案说明

1. 详情读取接口保持不变：`GET /api/stocks/{security_id}`
2. 新增同步接口：`POST /api/stocks/{security_id}/sync`
3. 同步服务负责外部抓取、最小清洗、去重与入库
4. 前端同步成功后重新请求详情接口

### 4.2 采用原因

- 与当前 stock detail v1 连续性最强
- 单股粒度最小，易于验证和调试
- 后续升级为批量同步或后台任务的扩展路径清晰
- 可把“同步失败”和“详情读取失败”清晰拆开

## 5. 架构与数据流

```text
Frontend
  StockDetailPage
    ├─ GET /api/stocks/{security_id}
    └─ POST /api/stocks/{security_id}/sync
            ↓
Backend API
            ↓
Stock Sync Service
   ├─ Announcement provider
   └─ News provider
            ↓
Data Layer
   ├─ announcements
   └─ news_items
```

### 5.1 读取流

1. 前端进入详情页
2. 请求 `GET /api/stocks/{security_id}`
3. 后端从本地数据库读取并聚合详情数据
4. 前端渲染详情页

### 5.2 同步流

1. 前端点击“同步公告 / 新闻”
2. 请求 `POST /api/stocks/{security_id}/sync`
3. 后端校验证券存在
4. 服务层拉取公告与新闻
5. 最小清洗、去重、增量写入
6. 返回同步结果摘要
7. 前端重新请求详情接口并刷新展示

## 6. 接口设计

### 6.1 读取接口（保持不变）

- `GET /api/stocks/{security_id}`

### 6.2 新增同步接口

- `POST /api/stocks/{security_id}/sync`

第一版建议无请求体，直接触发：

```http
POST /api/stocks/1/sync
```

### 6.3 返回结构建议

```json
{
  "security_id": 1,
  "synced": true,
  "announcement_count": 5,
  "news_count": 8,
  "synced_at": "2026-03-11T12:00:00",
  "warnings": []
}
```

### 6.4 错误与部分成功

- `security_id` 不存在 → `404`
- 公告成功 / 新闻失败 → 返回成功结果，但在 `warnings` 中体现
- 外部源完全失败 → 返回错误
- 已有详情数据不受同步失败影响

## 7. 数据更新策略

### 7.1 公告 / 新闻采用增量写入

- 已存在记录不重复插入
- 新记录增量写入

### 7.2 公告去重建议

优先使用最稳定的组合字段：

- `security_id`
- `title`
- `published_at`
- `url`

### 7.3 新闻去重建议

第一版采用最小逻辑去重：

- `security_id`
- `title`
- `published_at`
- `source`

### 7.4 同步窗口建议

第一版限制同步范围，例如：

- 最近 N 天新闻
- 最近 N 天或最近 N 条公告

目的是控制接口耗时与复杂度。

## 8. 前端交互设计

### 8.1 新增详情页操作按钮

- 文案：`同步公告/新闻`
- 位置：详情页顶部，靠近基础信息区

### 8.2 按钮状态

- 默认：`同步公告/新闻`
- 同步中：`同步中...`，按钮禁用
- 成功：显示“同步完成”，自动刷新详情
- 失败：显示“同步失败，请稍后重试”，保留旧数据

### 8.3 页面保持不变的部分

- 详情页原有结构不重做
- 只增强同步入口、同步状态、数据刷新链路

## 9. 模块推进顺序

建议按以下顺序推进：

1. `backend` + `data-layer` 联动推进
2. `frontend` 收口
3. `scripts` 仅在 provider 调试或本地联调需要时补充

## 10. 测试策略

### 10.1 backend / data-layer

重点验证：

- 同步成功
- 部分成功
- 外部源失败
- 不存在证券返回 `404`
- 增量写入与去重

### 10.2 frontend

重点验证：

- 点击同步按钮触发同步
- 同步中状态
- 同步成功后刷新详情
- 同步失败后显示错误并保留旧内容

## 11. 决策摘要

已确认的设计决策：

- 下一阶段为“信息聚合同步闭环 v1”
- 公告 + 新闻一起做
- 数据接入与存储优先
- 采用应用内触发同步
- 使用单股手动同步方案
- 读取详情与触发同步分离
